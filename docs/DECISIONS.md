### D22 in detail — how a driver gets into the app (2026-10-14)

**Decision.** Drivers never register themselves. Access to driver mode is granted by the supplier
(admin or dispatcher) and proven by the driver's phone number through the same OTP flow customers use.

**Flow.**

1. The admin opens _Settings → Drivers_ in the web panel and adds the driver: full name, phone (E.164),
   optional default mixer. The record is created with `isActive = true` and a `DriverProfile` linked to a
   `User` of role `DRIVER`. Optionally the system sends one SMS invite (i18n key, Phase 3): "Download CONCR
   and sign in with this number".
2. The driver installs the app, taps _Start_, types the number, enters the SMS code. There is no separate
   driver login screen and no role picker.
3. On `POST /auth/otp/verify` the server resolves the role from the phone: a phone with a `DriverProfile`
   → `DRIVER` and the app opens the driver tabs; an unknown phone → a new `CUSTOMER` account (self sign-up
   stays open for customers only); a phone whose user is `isActive = false` → `403 USER_INACTIVE`, no token.
4. The first driver screen shows the driver's name next to the shift switch so a wrong number is obvious;
   _Profile → Sign out_ is the way back.
5. When a driver leaves, the admin deactivates the record. Refresh tokens stop working at the next rotation,
   access tokens expire within minutes, and the driver's trips can be reassigned from the planning board.

**Rules.**

- One phone number = one user = one role. A driver who wants to order concrete needs a different number
  (not expected in MVP; a role switch can be added later without changing the data model).
- Phone changes are made by the admin, never by the driver (the number is the credential).
- The shift switch and the mixer assignment are the driver's and the dispatcher's business, not part of auth.
- Dev builds keep the "DEV: enter as driver" shortcut on the welcome screen; it runs the same OTP flow on the
  mock client and is compiled out of release builds.

**Amendment (owner, 2026-10-15).** After seeing the one-tap dev shortcut the owner asked that drivers
sign in explicitly and only when registered: the app's welcome screen has a separate "Sürücü girişi"
with a login (phone in any local format, or e-mail) and a password. The admin sets the initial password
when creating the driver and can reset it on the Drivers page; a driver's phone is refused by the OTP
flow (FORBIDDEN), so a driver can never end up with a customer account. Plate numbers are not accepted
as a login (they identify the truck, not the person). The dev shortcuts were removed from the app.

**Rejected alternatives.**

- _Plate number + password_: the plate identifies the truck, not the person; drivers rotate between mixers and
  two drivers can share one; passwords get shared, so the handover act would not say who delivered.
- _Email + password_: most drivers do not use email; forgotten passwords create a support flow for nothing.
  Email + password stays the staff login for the web panel (D10).
- _Invite code / QR_: a nice onboarding touch, not a replacement for phone + OTP; can be added on top later.

**Impact on code.** Mock (now): driver fixtures with phones `+9945000000 11/12/13`, OTP `123456`, the mock
`verifyOtp` already picks the role from the phone. Mobile (U2): no sign-up screen for drivers; dev shortcut
only. Web (U3): admin _Drivers_ page — list, add, edit, deactivate, assign a mixer. API (B1): role resolution
in `auth.service`, `USER_INACTIVE` error code, admin driver endpoints scoped by `supplierId`. Notifications
(Phase 3): optional `driver.invited` SMS.
